# Инструкция команде: память и адаптация

25 октября 2026 года. Перед началом обновить локальную ветку из `main`. Прочитать [концепцию](PROJECT.md), [ТЗ](TECHNICAL_SPEC.md) и [память и адаптацию](MEMORY_AND_ADAPTATION.md). Последний документ определяет новый этап M1; в нём есть данные, ограничения и критерии MA-01…MA-12. Это план реализации, а не объявление готовых функций.

## Front — текст задания

Развиваем True Path из разовой проверки в личную систему понимания. Твоя задача — интерфейс объяснимых связей и добровольного усвоения. Собственный сервер не добавляем, текущую навигацию и историю сохраняем.

1. Сначала вернуть возможность прочитать тип и объяснение связи графа; проверить FR-04/A-12. Не создавать связь только ради визуального эффекта.
2. С Back согласовать состояния и фикстуры M-01 до реализации потребителей. Пока Back делает хранилище, работать на фикстурах: загрузка, пустая память, нет подходящих связей, ошибка, недоступное основание, пересмотр вывода.
3. В результате исследования показать блок «Связано с тем, что вы уже изучали»: до трёх карточек. В каждой — два исследования/понятия, тип связи, «почему предложено», основания, ограничения и действия принять/отклонить. Переход к старому исследованию не запускает новый API-запрос.
4. Предложить сохранить понятие и ответить на один вопрос. Различать самооценку и оценку ответа; дать исправить спорную оценку. Посещение экрана и лайк не отмечать как усвоение.
5. Добавить локальную очередь «Вернуться к важному», отложить/отключить повторения и объяснение выбранной даты. Не навязывать push-уведомления и не обещать, что человек больше ничего не забудет.
6. Показать журнал эпизодов источника: что утверждалось, какие основания расходятся, статус проверки и исправления. Не рисовать единый «процент правды» или рейтинг эрудиции.
7. Отдельно оформить сброс персонализации и удаление знаний. Новые/исправленные основания помечать явно; изменения прошлого вывода не скрывать.

Результат: PR с интерфейсом M-03/M-04/M-05 на общем контракте, обновлёнными визуальными эталонами и описанием состояний. Проверить обычный CI, отдельно Paparazzi; жесты и системное поведение не считать проверенными по статическим снимкам. В PR указать выполненные MA-пункты и неисполненные device-проверки.

**Первый PR Front:** объяснения связей + карточка одного мостика на фикстурах. До утверждения Back-контракта не внедрять параллельную собственную схему хранения.

## Back — текст задания

Твоя область — доменные данные и внешние API внутри Android, не отдельный сервер. Нужно обеспечить постоянную проверяемую память и основания адаптации. Начинаем с локального M1; платный API не должен блокировать фикстуры и хранение.

1. Закрыть пробел `startArticle`: сохранять полный снимок прочитанной статьи с медиаблоками, источником и доступными локальными материалами, а не один заголовок. Для старой истории не выдумывать недостающий снимок.
2. Подготовить M-01: точные Kotlin-типы и операции из раздела 7 MEMORY_AND_ADAPTATION, совместно проверить их с Front и обновить API_CONTRACT. Отдельные сущности для фактического статуса, предложенной связи, решения пользователя и попытки усвоения.
3. Реализовать Room и миграцию существующей JSON-истории без потерь. Материалы хранить в постоянном внутреннем каталоге, не кэше. Добавить экспорт/импорт с версиями, проверкой формата и повторным импортом без дублей; не экспортировать ключи.
4. Сделать извлечение кандидатов по ссылкам, сущностям и полнотекстовому поиску. Возвращать до трёх связей с основаниями; пока их нет — пустой результат, а не выдуманная ассоциация. Embeddings и модельное объяснение подключать позже, отдельно и с ограниченной выборкой личного контекста.
5. Сохранять один вопрос/попытку/срок повторения и происхождение оценки. Изменение исходного вывода инвалидирует зависимый вопрос до пересмотра.
6. Реализовать журнал проверяемых эпизодов источника: кандидат, проверка с основанием, исправление/отмена. Мнение модели и жалоба пользователя не являются доказанным эпизодом ошибки. Учесть тему, даты, число проверенных случаев и зависимые пересказы. Не менять веса автоматически на этапе M1.
7. Принятие аналогии не меняет статус факта. Учебные записи не влияют на реальную статистику. Локальное чтение и обратная связь не создают платные задачи. Удаление очищает копии/индексы и корректно помечает зависимые знания.

Результат: PR с миграцией, контрактом, фикстурами и тестами MA-01…MA-12 своей области; зафиксированные ограничения. Реальная интеграция E0/B-04 остаётся отдельным обязательством прежнего ТЗ. Будущие веса M2 требуют сравнительной проверки с базовой политикой, версионирования и отката.

**Первый PR Back:** схема контракта + снимок статьи + план и тестовые случаи миграции. После согласования — хранилище, без монолитного PR на весь второй мозг.

## Как интегрируемся

1. Front и Back сначала согласуют M-01 и общий учебный пример из раздела 6 MEMORY_AND_ADAPTATION. Предлагаемые типы не выдаём за уже реализованные.
2. Параллельно Front делает состояния на фикстурах, Back — миграцию и хранилище. Общие `domain/`, ViewModel и Gradle меняем согласованно через небольшие PR.
3. Первый общий сценарий: два сохранённых исследования → объяснимый мостик → решение пользователя → один вопрос → перезапуск → сохранённый результат и очередь повторения.
4. Мы, DevOps/Pipeline, проверяем PR, воспроизводимость, миграции, отсутствие скрытых платных вызовов и новые контракты. В обычном CI оставляем компиляцию, ненулевой набор unit-тестов и Lint; Room/instrumentation и визуальные проверки добавляем по выбранному способу тестирования, не объявляя их готовыми заранее.
5. Каждый PR содержит: ID задачи, изменения контракта/данных, выполненные проверки, ограничения, способ отката с учётом миграции. Откат кода сам по себе не откатывает схему базы — разрушительный сброс пользовательской памяти недопустим.

Не объединяем M1 с обучением собственной модели, глобальным рейтингом источников, сервером, синхронизацией и обещанием гарантированной памяти. Сначала проверяем работоспособность и полезность одного полного цикла.
