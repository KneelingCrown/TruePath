# True Path — техническое задание MVP

Версия: 0.2 от 25 октября 2026 года. Статус: рабочее ТЗ для команды из трёх участников. Основание — [концепция](PROJECT.md). Текущее состояние реализации описано в [README](../README.md), требования к исследовательскому адаптеру — в [API_CONTRACT.md](API_CONTRACT.md).

## Расширение ТЗ: этап M1

Добавлен этап постоянной личной памяти, ассоциаций, добровольного усвоения и журнала качества источников: [MEMORY_AND_ADAPTATION.md](MEMORY_AND_ADAPTATION.md). Он входит в план команды и имеет отдельную приёмку MA-01…MA-12; пока не реализован. [Инструкция Front и Back](TEAM_HANDOFF.md) определяет первые PR и зависимости.

Разделы ниже сохраняют требования к базовому MVP и E0–E3. В части персонализации прежнее отнесение её целиком «после MVP» уточняется: локальная объяснимая адаптация M1 добавлена сейчас, автоматические веса источников и расширенная рекомендательная система остаются последующими этапами. Готовность M1 на учебных данных не заменяет приёмку реальной интеграции.

## 1. Результат работы

Разработать Android-приложение, в котором пользователь читает ленту, явно запускает проверку новости или собственного материала, наблюдает построение графа доказательств и повторно открывает сохранённый результат без нового платного запроса. Для учебного сценария показать связь утверждения с задачей и объяснимый «План Б».

Собственный сервер не создаётся. Android-клиент напрямую обращается к внешним сервисам. Роль **Back** означает разработку интеграционного и доменного слоя приложения, а не развёртывание бэкенда.

Работа завершается двумя отдельно проверяемыми результатами:

- **Учебная демонстрация:** воспроизводимый сценарий без платных API, явно обозначенный как демонстрация. Нужен для разработки, CI и презентации при недоступности сервиса.
- **MVP с реальной интеграцией:** получение новостей и исследование через проверенные внешние API. Учебная демонстрация не заменяет приёмку реального исследования.

## 2. Объём и ограничения

| В MVP | После MVP |
| --- | --- |
| Четыре вкладки: Лента, Проверить, Граф, История; настройки источников, интересов и API | Аккаунты и синхронизация между устройствами |
| Ограниченный согласованный список источников, группировка событий, устранение дублей, фильтрация и простое ранжирование | Расширенная рекомендательная система, автоматическое обновление исследований |
| Текст, ссылка, скриншот или изображение с явным указанием полноты обработки | Видео, аудио и произвольные документы с полной обработкой |
| Асинхронное исследование, промежуточный граф, восстановление по ID задачи | Собственный исследовательский сервер |
| Локальная история с исходными материалами и графом | Универсальное определение дипфейков |
| Одна связанная задача и карточка «План Б» в учебном сценарии | Полноценный таск-менеджер |

Сохраняется стек репозитория: Kotlin 2.1.21, Jetpack Compose, Material 3, coroutines/Flow, Java 17, minSdk 26, compileSdk/targetSdk 36, AGP 8.13.2, Gradle 8.13. Изменения версий и новые зависимости обосновываются в отдельном PR.

Для первой версии допускается одна активная проверка. Сохраняются ограничения прототипа: до 12 000 символов текста и до пяти вложений. Если лимит поставщика меньше, интерфейс сообщает об этом до отправки; текст и файлы не обрезаются молча. Поддерживаемые MIME-типы и размеры файлов фиксируются после проверки API.

## 3. Команда и границы ответственности

| Участник | Ответственность | Результат для остальных |
| --- | --- | --- |
| **DevOps/Pipeline — автор проекта и Codex** | Среда, CI, правила интеграции, отчёты проверок, сборка по отдельному запросу | Повторяемая проверка любого PR без ключей и платных вызовов |
| **Front** | Compose-экраны, навигация, состояния UI, доступность, граф, отображение настроек и ошибок | Полный сценарий на учебных данных и подключение общего контракта |
| **Back** | Выбор и проверка API, сетевые адаптеры, доменные модели и редуктор, загрузка материалов, локальное хранение, восстановление задач | Стабильные данные и события для Front, работающие интеграционные сценарии |

Front владеет `ui/` и пользовательским поведением `TruePathViewModel`; Back — `data/` и `domain/`. Подключение зависимостей во ViewModel, изменения общих моделей и Gradle согласуются через PR до параллельного редактирования. DevOps/Pipeline владеет CI и инструкциями среды. Каждый участник пишет проверки своей части; DevOps организует их запуск, но не принимает на себя все тесты проекта.

## 4. Пользовательские требования

### 4.1. Лента — FR-01

- При первом запуске пользователь выбирает темы; настройки можно изменить позже. До выбора допускается общая лента с пояснением.
- Карточка показывает заголовок, источник, дату, тему, краткое описание и действие «Проверить». Несколько публикаций об одном событии доступны из общей карточки.
- Back реализует минимальную объяснимую группировку: точные дубли по нормализованному URL или идентификатору источника; предполагаемое объединение разных публикаций помечается как группировка по сходству. Оно не доказывает копирование и не объединяет статусы достоверности.
- Для MVP достаточно детерминированного ранжирования по выбранным темам, свежести и признаку просмотра. Правила описываются в документации. Сохранения, скрытия и обучение предпочтениям относятся к следующему этапу.
- Получение ленты, открытие новости и формирование описания не запускают исследование. Действие запуска доступно только явно. Краткое описание не маркируется как проверенный вывод.
- При ошибке обновления остаётся доступна сохранённая лента с датой последнего обновления. Предусмотрены состояния загрузки, пустого результата и повтора запроса.

### 4.2. Материалы и запуск — FR-02

- Во вкладке «Проверить» доступны текст, ссылка, вставка из буфера, выбор и удаление изображений через системный диалог. Пустой запрос отправить нельзя.
- Перед сетевой отправкой пользователь видит поставщика, состав передаваемых данных и предупреждение о возможной стоимости. При неоднозначном предмете проверки может уточнить контекст до запуска.
- Изображения передаются только при подтверждённой поддержке выбранного API либо отдельного OCR/vision-сервиса. Результат сообщает, обработан ли текст, изображение или оба вида данных. Неподдерживаемый файл сохраняется локально с пояснением и не выдаётся за проанализированный.
- Локальная запись и исходный материал сохраняются до удалённого запуска. После ответа поставщика сохраняется его ID задачи. Повторный тап не создаёт вторую задачу.
- URI из Android не передаётся как публичный URL. Чтение выполняется через `ContentResolver`; доступность, формат и размер проверяются до отправки.
- При потере ответа на создание задачи клиент сначала использует механизм идемпотентности или поиска задачи поставщика. Если такой возможности нет, показывает неопределённость запуска и не повторяет платный запрос автоматически.

### 4.3. Исследование и навигация — FR-03

- После запуска сразу открывается «Граф» с исходным материалом и текущим этапом. Проценты готовности показываются только при наличии достоверных данных поставщика.
- До завершения появляются структурированные утверждения, источники и доказательства. Предварительность выводов обозначается текстом.
- Если пользователь остаётся в графе, завершение обновляет текущий экран без сброса камеры. Если он перешёл на другую вкладку и приложение активно, завершение открывает итоговый граф согласно концепции. В фоне экран принудительно не открывается; при возвращении доступен сохранённый результат.
- Потеря соединения, остановка получения событий и ошибка API сохраняют полученные данные. Обрыв потока без подтверждения завершения не означает успех.
- «Остановить получение» прекращает локальное наблюдение. Отмена удалённой задачи — отдельная операция, доступная только при поддержке поставщика; прекращение наблюдения не обещает остановить расходы.
- После перезапуска приложение восстанавливает локальную запись и получает состояние существующей задачи. Новое исследование автоматически не создаётся.

### 4.4. Граф и выводы — FR-04

- Обязательны узлы материала, утверждения, источника и доказательства; для учебного «Плана Б» добавляется связанная задача. Событие может оставаться сущностью ленты без отдельного узла MVP.
- Для утверждения отображаются текст, статус, объяснение и предварительность. Для доказательства — конкретная цитата или фрагмент и ссылка на источник; для источника — название, URL или сохранённый материал, дата при наличии.
- Каждая содержательная связь имеет тип и объяснение. Нажатие на связь открывает основание; предполагаемая связь визуально и текстом отличается от установленной.
- Зелёный — поддерживается; жёлтый — недостаточно данных или существенное расхождение; красный — противоречит доказательствам; серый — не проверено. Цвет дублируется текстом или значком. Оценка относится к конкретному утверждению и контексту.
- Доступны масштабирование, перемещение, выбор узла и «Показать весь граф». Новые события сохраняют существующие координаты, камеру и выбранный узел. Layout рассчитывает Android-клиент.
- Узлы и доказательства доступны также списком для чтения и средств доступности. После завершения исследования пульсация прекращается.

### 4.5. История и хранение — FR-05

- Сохраняются текст, вложения, дата, режим demo/real, поставщик, локальный ID, удалённый ID задачи, этап, статус, граф, итог и данные восстановления потока.
- История поддерживает поиск по теме или тексту, открытие и удаление. Завершённый граф открывается офлайн без сетевого запуска. Для незавершённого допустим запрос состояния существующей задачи.
- «Обновить исследование» — отдельное подтверждаемое действие с предупреждением о стоимости. Создаётся новая связанная запись; прежний результат сохраняется.
- Изображения копируются во внутреннее хранилище приложения либо используется доказанно устойчивый доступ к URI. После перезапуска исходный материал должен открываться. Для MVP предпочтительна локальная копия в пределах лимитов.
- Запись снимка атомарна. Версия формата и миграция сохраняют уже существующую историю прототипа. Повреждение файла не приводит к молчаливой потере данных: сохраняется возможность восстановления и показывается ошибка.
- Удаление записи очищает принадлежащие только ей внутренние копии вложений, но не оригиналы пользователя. Не обещается удаление данных у поставщика без подтверждённой операции его API.

### 4.6. «План Б» — FR-06

В учебном сценарии утверждение связано с задачей «Изменить время выезда». Карточка показывает основание зависимости, текущую неопределённость и действие «Уточнить направление по расписанию». Предложение не изменяет задачу автоматически. Пользователь может принять или отклонить его; выбор сохраняется локально. Произвольное управление задачами и генерация персональных планов не входят в MVP.

### 4.7. Настройки и ключи — FR-07

Предусмотреть настройки тем, источников и выбранных API. Пользователь вводит собственный ключ или использует поддерживаемую поставщиком клиентскую авторизацию. Секреты не попадают в Git, APK, историю исследования, резервные копии и логи. Для локально сохраняемого ключа используется шифрование с ключом из Android Keystore; доступны замена и удаление. Если поставщик запрещает прямой Android-доступ или требует общий серверный секрет, он не подходит для принятой архитектуры.

При отсутствии ключа доступны лента в пределах возможностей источника, история и явно выбранная учебная демонстрация. Попытка реального исследования показывает, чего не хватает; автоматической подмены демонстрацией нет.

## 5. Контракт Front ↔ Back

Существующий `ResearchSource.events(session): Flow<ResearchEvent>` сохраняется как отправная точка. Он пока не описывает удалённый запуск, курсор или авторизацию. На этапе E1 Back уточняет контракт в [API_CONTRACT.md](API_CONTRACT.md), а Front проверяет, что он покрывает состояния UI. Следующее — требования к будущему контракту, а не уже реализованные методы.

| Операция | Обязательное поведение |
| --- | --- |
| Загрузить ленту | Вернуть публикации, группы, время обновления и состояние ошибки/кэша |
| Создать исследование | Принять локальный ID и проверенный ввод; вернуть удалённый ID и режим выполнения; исключить повторное создание |
| Наблюдать исследование | Выдавать валидированные доменные события либо изменения частичных снимков |
| Восстановить исследование | Использовать сохранённый удалённый ID и курсор; при отсутствии курсора — согласованный снимок |
| Прочитать/сохранить историю | Работать локально, сохранять формат и возможность миграции |
| Остановить наблюдение / отменить задачу | Различать локальную остановку и подтверждённую удалённую отмену |

Доменные расширения относительно прототипа: `providerId`, `remoteTaskId`, курсор или ревизия, время обновления, версия схемы, признак demo/real; объяснение и предварительность связи; связь доказательства с источником; связанная задача и решение пользователя. Точные Kotlin-типы фиксируются в E1 до реализации потребителей. Секреты не входят в эти модели.

События сохраняют постоянные ID узлов и связей. Повторное событие применяется один раз, изменение сущности получает новый ID события. Если поставщик не выдаёт ID, адаптер строит устойчивый идентификатор из версии сущности или снимка; случайный UUID при каждой доставке недопустим. Порядок обновлений определяется курсором/ревизией поставщика, а не локальным временем доставки; устаревшая версия не перезаписывает новую.

Сохраняются семантики `Stage`, `UpsertNode`, `UpsertEdge`, `Finished`, `Failed`, `NeedsApi`. Связь ждёт появления обоих концов. Пропущенные зависимости после завершения отражаются как неполные данные, а не как доказанные связи. `NeedsApi` остаётся локальным статусом прототипа. Адаптер различает временную потерю соединения, требующую восстановления наблюдения, и окончательную ошибку исследования; поздний `Finished` не превращает терминальную ошибку в успех.

Частичный JSON и текстовые токены отчёта не публикуются как готовые доказательства. Снимок и его курсор сохраняются согласованно: после сбоя допустим повтор уже применённых событий, но не пропуск несохранённых. Завершённая задача не принимает поздние изменения без явного нового исследования.

Для совместной разработки Back предоставляет обезличенные фикстуры: успешная проверка, недостаток данных, пересмотр статуса, дубль, связь до узлов, обрыв и восстановление, ошибка авторизации, превышение лимита, повреждённый ответ. Front использует их до доступности реального сервиса.

## 6. Проверка поставщиков — обязательный этап E0

Back проверяет исследовательский API, источник новостей и при необходимости OCR/vision. Результат оформляется в `docs/PROVIDERS.md` при выполнении задачи: официальная документация, дата проверки, поддерживаемые материалы, прямой Android-доступ, ограничения, стоимость, хранение/удаление данных и результаты испытаний. Конкретные сервисы и URL методов этим ТЗ не выдумываются.

Исследовательский сервис принимается только при доказанной возможности получить структурированные промежуточные источники и доказательства, восстановить асинхронную задачу по ID и однозначно определить завершение/ошибку. SSE, NDJSON или частичные снимки допустимы; получение только итогового отчёта не проходит этот этап.

Проверить минимум три русскоязычных случая: утверждение с подтверждением, утверждение с противоречием первичному материалу и случай с недостатком данных. Записать наблюдаемые результаты, стоимость и задержки, не представляя эти примеры как общую оценку точности. Отдельно проверить изображение и сценарий восстановления задачи. Для новостей зафиксировать согласованный набор не менее двух доступных источников и условия их использования.

До платного испытания владелец проекта задаёт бюджет и предоставляет доступ безопасным способом. До этого Back работает с документацией и фикстурами, Front — с учебным источником, DevOps — с CI. Если подходящий API не найден, фиксируется блокер реального MVP; команда продолжает учебную демонстрацию, не меняя молча архитектуру или обязательный потоковый сценарий.

## 7. План работ и задачи

Этапы задают порядок зависимостей, а не календарные обещания. Оценки и даты команда добавляет после E0/E1.

| ID | Владелец | Задача и проверяемый результат | Зависимости |

## 8. Нефункциональные требования и CI

- UI и сообщения об ошибках на русском. Сетевые операции, чтение файлов и запись истории не блокируют главный поток. Ошибки включают понятное действие для пользователя.
- Базовый предел автоповторов наблюдения — три попытки с увеличением задержки и учётом `Retry-After`; затем доступен ручной повтор. Создание платной задачи не повторяется без гарантии идемпотентности. Конкретные тайм-ауты, лимит длительности и расходов фиксируются в E0 согласно возможностям сервиса.
- Учебный граф из 100 узлов и 150 связей остаётся интерактивным при добавлении событий; обработка одного валидного события до отображения — не более 1 секунды на выбранном командой тестовом устройстве. Модель устройства, способ измерения и результаты записываются в протоколе; это целевой критерий, а не заявленная характеристика текущей версии.
- HTTPS и проверка сертификатов обязательны. Недоверенный ответ API валидируется до применения. Ссылки открываются только как допустимые HTTP(S)-адреса с отображением адреса; произвольные URI из ответа не исполняются.
- Логи содержат технический этап и безопасный идентификатор, но не ключи, исходные материалы, содержимое вложений или полные ответы с персональными данными.
- Обычный CI запускает `./gradlew --no-daemon --max-workers=4 :app:compileDebugKotlin :app:testDebugUnitTest :app:lintDebug`. Ошибка любого шага блокирует успешный результат. Unit-тесты должны реально выполняться; нулевое число тестов не принимается. Новые ошибки Lint не подавляются ради зелёного CI, предупреждения разбираются в PR.
- Проверки реального API запускаются отдельно и явно, с пользовательским доступом и бюджетом; не входят в CI каждого PR. Ключи не нужны для учебного режима и доменных тестов.
- По текущему правилу проекта CI не создаёт APK/AAB. Проверка интерфейса требует отдельного разрешённого запуска на устройстве/эмуляторе и тестового installable-артефакта. До этого device-пункты приёмки остаются непроверенными; успешная компиляция их не заменяет.

## 10. Готовность задачи и MVP

Задача считается выполненной, когда код прошёл ревью, относящиеся к изменению тесты и общий CI; описаны изменённые контракты и ограничения, а в PR приложен результат проверки поведения. Изменение UI сопровождается снимком или записью после разрешённой проверки на устройстве. Общие модели проверяют оба разработчика; pipeline — DevOps/Pipeline.

Учебная демонстрация принимается отдельно по применимым пунктам с отметкой demo. Реальный MVP принимается после подтверждения поставщика, прохождения всей матрицы в соответствующих режимах и проверки обязательных экранов на Android 26 и 36. Недоступный API, отсутствие бюджета или неисполненные device-проверки остаются явными блокерами соответствующей части приёмки.

Перед завершением команда сдаёт: исходники, инструкции среды и CI, обновлённый API_CONTRACT.md, PROVIDERS.md с результатами E0, протокол приёмки, сценарий учебной демонстрации и перечень известных ограничений. На данном этапе эти результаты ещё предстоит реализовать; это ТЗ не объявляет их готовыми.
