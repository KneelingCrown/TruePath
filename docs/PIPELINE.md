# Проверки и контроль изменений

## Автоматические проверки GitHub

Workflow [Android checks](../.github/workflows/android-checks.yml) запускается на push в любую ветку, на pull request и вручную. Он устанавливает JDK 17 и Android SDK 36 / Build Tools 35.0.0, проверяет Gradle Wrapper и выполняет:

```bash
./gradlew --no-daemon --max-workers=4 :app:compileDebugKotlin :app:testDebugUnitTest :app:lintDebug
python3 scripts/check_test_results.py app/build/test-results/testDebugUnitTest
```

Нулевой набор тестов, все пропущенные тесты, ошибки или противоречивые JUnit-отчёты приводят к ошибке CI. Пропущенные тесты учитываются отдельно. При ошибке компиляции отсутствие тестов не считается успешной проверкой. При обычном завершении, включая ошибку, отчёты тестов и Lint сохраняются в артефактах на 14 дней. При отмене запуска отчёты могут отсутствовать. Повторный push в ту же ветку отменяет устаревший запуск.

Проверки не создают APK/AAB, не обращаются к платным исследовательским API и не требуют пользовательских ключей. GitHub Actions получает только право чтения содержимого. Кэш PR и веток, отличных от main, доступен для чтения; обновление выполняется из main. Тесты интерфейса на устройстве пока не включены.

Наличие workflow само по себе не запрещает merge или push при ошибке. Для обязательного контроля нужна настройка ruleset/защиты main с required check `Compile, unit tests, lint`. Пока она отдельно не настроена, это рекомендация, а не действующая гарантия. Прямые push в main сейчас разрешены владельцем проекта.

## Разбор изменений команды

DevOps/Pipeline при разборе каждого нового коммита проверяет:

- Соответствие задачам и ограничениям [ТЗ](TECHNICAL_SPEC.md), владельца и зависимости изменения.
- Изменения общих моделей, API-контракта, миграции истории и совместимость Front/Back.
- Явный запуск платного исследования, отсутствие ложного успеха, восстановление удалённой задачи без повторного создания.
- Секреты, сетевые назначения, зависимости и изменения CI.
- Результаты компиляции, тестов и Lint; device-проверки отмечаются отдельно.

Сообщение в рабочем чате: SHA и автор → что изменилось → найденные проблемы с файлами и строками → результат CI или «не проверен» → следующее действие. Комментарий автора является контекстом, а не доказательством корректности кода. При отсутствии замечаний явно указываются пределы проверки.

Локальный наблюдатель в облачной среде может периодически получать Git refs, сообщения коммитов и список файлов. Это журнал изменений, а не автоматическое семантическое ревью. Его процесс зависит от жизни текущей среды, не переносится в новые задачи и не может самостоятельно писать в чат. Отдельные комментарии и обсуждения GitHub PR через Git не поступают; для их разбора требуется доступ к GitHub API либо предоставленный текст. Постоянную автоматическую проверку изменений обеспечивает GitHub Actions; анализ в чате выполняется при активной работе с Codex.

## История разработки и визуальные проверки Front

[DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md) сохраняет задачи, решения и выполненные проверки этапов. Подробные сообщения коммитов дополняют журнал и позволяют восстановить последовательность разработки.

Дополнительные снимки Compose на компьютере включаются отдельно, без APK:

```bash
./gradlew :app:verifyPaparazziDebug -Pscreenshots
```

Paparazzi сравнивает 17 эталонов из `app/src/test/snapshots/images/`, включая тёмную тему, большой граф и конец статьи. Перед намеренным обновлением дизайна используют `:app:recordPaparazziDebug -Pscreenshots` и визуально просматривают каждый изменённый эталон. Этот режим пока не добавлен в GitHub Actions и не заменяет device-проверки. На этапе 04 обычный набор содержит 28 модульных тестов; CI также выполняет компиляцию и Lint.
